# Secure Supabase migration delivery

## Goal
Ensure migrations are verified before promotion and applied to the configured Supabase database only after a reviewed `dev` → `main` promotion and a protected GitHub Environment approval. The API currently exposes a generic 500 when the organization-list RPC receives a 404 from Supabase; the live database's migration state is still unverified.

## Decisions and boundaries
- User selected preparation of CI **and** remote `dev` → `main` promotion, with separate explicit confirmation for every remote mutation and for applying migrations to a real database. No push, PR, merge, branch/ruleset/environment/secret mutation, or real database migration is authorized by this task document alone.
- API repository default branch is `main`; it has no advertised remote `dev`. Read-only GitHub queries returned zero configured environments, repository secrets, and rulesets; the branch-protection endpoint returned 404 (not proof of authorization to create protection). Preserve unrelated `.gitignore` changes and the existing Users feature branch.
- Existing `.github/workflows/ci.yml` references nonexistent `ZonarHub.sln` and `global.json`; actual solution is `ZonarHub.slnx`. Existing PostgreSQL 17 disposable harness `supabase/tests/run_complex_courts_atomic.sh` applies every migration and verifies service-role-only RPC access. Do not use mock-only tests as proof of a deployed function.
- Reference `montesgp/receipt-risk-detector` was read via GitHub: its CI checks `dev`/`main`, and PR validation enforces issue approval, type label, and `dev` → `main` source. Those workflows do **not** deploy Supabase migrations; adapt policy, do not copy a nonexistent deployment gate.
- On Supabase CLI 2.109.0, `supabase db push` supports `--db-url` and `--dry-run`. Never enable `--include-all`, seed, or automatic remote repair to paper over history drift. Target identity, credentials, and approval gate must be explicit and auditable. Use least-privilege GitHub Actions permissions; never print a database URL or user token.

Trust model (security correction after independent verification): a plain `pull_request` trigger runs the workflow file from the PR head, so a same-repository `dev` PR could edit or neuter its own gate. `pull_request_target` evaluates the definition from the base branch `main`, so changes to the gate take effect only after they are merged. That trusted context is safe here only because the job never checks out, fetches or executes PR code, uses no actions, caches, artifacts, `GITHUB_ENV`/`GITHUB_OUTPUT`/`GITHUB_PATH`, secrets or token scopes, and reads PR fields solely as data; static tests fail on any of these. Consequence: this PR gate must reach `main` before it protects promotions, and the first PR that introduces it is judged by whatever `main` contains (nothing yet). Untrusted PR fields reach the step only through `env` and are read by a `shell: python` script, so no shell evaluates them and no PR-controlled value is echoed (no workflow-command injection). It fails closed when the head repository differs from or is missing versus the base repository (forks), the source is not exactly `dev`, the base is not `main`, or the body lacks a local `#N` reference (`owner/repo#N`, `#0`, `&#35;`, `word#N` and URL fragments do not count); the reference is not looked up, so it proves neither issue existence nor approval. RED: the 15 new tests errored with `FileNotFoundError` for the missing workflow while the existing 36 passed; GREEN: 51/51 after two test-precision fixes (prose "Pull requests" matched `requests`; the integer PR number is allowed only in the concurrency group). Four in-memory mutants (no fork check, loose issue regex, echoing the body, unchecked base) were each killed by the behavior tests, which execute the workflow's exact script.
