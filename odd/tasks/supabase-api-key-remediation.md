Official references: [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys), [migrating to new API keys](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys), [legacy key rotation](https://supabase.com/docs/guides/troubleshooting/rotating-anon-service-and-jwt-secrets-1Jq6yd). Supabase documents that new keys coexist with legacy keys until legacy keys are separately disabled at Project Settings → API Keys.

## Known boundaries
- The API's `ZonarHub.ApiService/appsettings.Development.json` is tracked and contains `Supabase:Key` for that shared project. It is not a runtime secret store; removing it does not remove the value from Git history.
- `ZonarHub.Infrastructure/Persistence/Supabase/SupabasePersistenceExtensions.cs` sends the same value as `apikey` and `Authorization: Bearer`; a non-JWT `sb_secret_…` must not be sent as Bearer. `Supabase__Key` overrides the JSON configuration through standard ASP.NET Core environment precedence; restart is required because the named client uses `IOptions<SupabaseOptions>`.
- The Angular source has no direct Supabase client or publishable key markers, but deployed/external consumers are unverified. The API signs its own user JWTs with a different setting; the database-migration workflow uses a PostgreSQL password, not this API key.
- The user confirmed the API currently runs only on their machine; Azure/Railway/AWS are future possibilities, not known deployed hosts. External consumers still require inventory before disabling legacy keys. The `service_role` key was public; no validity/rotation check using it is allowed. The Dashboard account/owner has not been established yet. AppHost does not explicitly forward `Supabase__Key`, so the runbook uses standalone API startup first.
- Current migration history is 18/20. The hardened but unapplied impersonation and complex/court migrations require separate specific database approvals after the credential incident is contained.
